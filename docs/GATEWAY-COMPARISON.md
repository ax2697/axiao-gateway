# AI 网关能力对标（2026-11）

对标对象：LiteLLM、Portkey、new-api、one-api、Envoy AI Gateway、Bifrost、Sub2API。
参考来源见文末。这张表的用途是**决定下一步做什么**，不是抄功能清单。

## 一、行业公认的四大支柱

各家的宣传口径不同，但拆开看都是这四块：

1. **统一抽象与路由** —— 一个 API 对接所有厂商，协议互转，模型映射
2. **弹性与容错** —— 负载均衡、自动降级、熔断、重试退避、限流
3. **可观测性与成本** —— 请求追踪、token/成本统计、审计日志、预算告警
4. **安全与缓存** —— 鉴权与密钥管理、请求/响应缓存、护栏

## 三、本轮补的两项及其取舍

### 失败降级 + 熔断

行业里最关键、也最容易被做成"看起来有"的一项。三个必须想清楚的点：

**1. 什么错误该换渠道**

Portkey 的默认行为是"任何非 2xx 都降级"，然后允许用 `on_status_codes` 收窄。
我们没有采用这个默认值，因为全量降级会把"模型拒绝回答"（内容策略）这种
业务性失败当成基础设施故障，白白重试一遍还可能换个模型再说一遍。

我们只对 **429 / 5xx / 连接失败** 降级。400/401/403/404/413/422 直接如实返回。

**2. 冷却多久**

LiteLLM 的默认是 `cooldown_time: 5s`，规则是「429 立即冷却、分钟失败率 >50%
冷却、401/404/408 冷却」。我们的场景是**免费额度**，特点不同：

- 429 是常态（额度小），所以冷却要短（5 秒），尽快回到池子
- 401/403/404 是自己配置错了，重试无意义，冷却要长（60 秒）
- 5xx 可能是对方抖动，连续 3 次才判定（避免误杀）

**3. 冷却的粒度**

LiteLLM 的 cooling 是**按部署（单个渠道）**做的，不是按模型组。
这点很重要：三条同平台的 Key 挂了一条，另外两条必须照常服务。
我们的实现也是按 `upstream.id` 隔离。

### 响应缓存

多数网关默认开启，我们反过来做了很多"不缓存"的限制：

| 规则 | 理由 |
|---|---|
| 温度 > 0 不缓存 | 用户调高温度就是要每次不一样，缓存会让"重新生成"失效 |
| 带 tools 不缓存 | 工具调用依赖外部状态，旧结果比没结果更糟 |
| 流式不缓存 | 缓存后拼 SSE 是假流式，体验退步 |
| 错误不缓存 | 否则重试十次都是同一个错 |

## 六、按错误类型降级（0.7.0 的关键修正）

这是本轮最重要的一条，也是之前判断错的地方。

### 400 里其实混着三种相反的情况

LiteLLM 把 400 拆成三个专门的异常类型，这不是洁癖，是因为处理方式正相反：

| 400 的真实原因 | LiteLLM 异常 | 该怎么做 | 我们的旧行为 |
|---|---|---|---|
| 上下文超长 | `ContextWindowExceededError` | 换窗口更大的渠道**一定成功** | ❌ 当请求错误，直接失败 |
| 内容策略拒绝 | `ContentPolicyViolationError` | 换同厂商无用，异厂商或自建模型可能行 | ✅ 不降级（碰巧对） |
| 参数不支持 | `BadRequestError` | 换谁都一样，别浪费配额 | ✅ 不降级 |

**上下文超长是所有失败类型里唯一"换个更大的模型就一定能成功"的**——
上下文装不下是纯容量问题，没有随机性、没有服务商差异。

不单独处理它的代价：长文档问答、合同审阅、RAG 拼接（召回条数一多 prompt 就失控）、
多轮客服（历史累积到某回合突然爆掉）、代码库分析，这些场景会稳定失败。

### 我们现在的判定

按响应体内容匹配关键词（三家真实措辞都覆盖了）：

```
OpenAI    "This model's maximum context length is 8192 tokens"
Anthropic "prompt is too long: 201234 tokens > 200000 maximum"
Gemini    "The input token count (1048576) exceeds the maximum number of tokens allowed"
```

**宁可漏判也不误判**：把"参数错误"误判成"上下文超长"会白跑一整条降级链，
代价比漏判大得多。

### 一个反直觉的配套规则

**上下文超长不让渠道进冷却。**

它不是渠道坏了，是这个请求太大。如果按普通失败冷却 30 秒，紧接着那个
本来能正常跑的小请求也会被无谓跳过。

### 调用前预检

LiteLLM 的 `enable_pre_call_checks` 思路很实用：**发之前就跳过窗口不够的渠道**。

不预检的代价：把 5 万 token 的 prompt 发给 8K 窗口的模型 → 等它返回 400 →
换下一个。白花一次往返，部分厂商还按输入计费。

我们的估算**刻意偏保守（低估）**：真实 tokenizer 拿不到（各家不同、要额外依赖），
**高估会误杀本来能成功的请求，那比多试一次更糟**。所以中文 1 字 1 token、
其它 4 字符 1 token，且只有明确超出才跳过，不设 95% 之类的收紧系数。

## 四、下一步建议（按性价比）

| 能力 | 工作量 | 价值 | 建议 |
|---|---|---|---|
| **请求追踪 ID** | 低 | 高 | 值得做：一个 `X-Request-Id` 贯穿日志、账本、响应头 |
| 预算告警 | 低 | 中 | 日消费超阈值写日志 + 界面提示 |
| 按 Key 的 RPM 限流 | 中 | 中 | 多人共用才需要 |
| 成本/延迟感知路由 | 中高 | 中 | 要有价格表和延迟样本，单上游时没意义 |
| 语义缓存 / 语义路由 | 高 | 低 | 要模型，跟"单 exe"定位冲突 |
| 护栏 / PII 脱敏 | 中高 | 低 | 合规场景才需要 |

**明确不做的**：语义缓存、语义路由、SSO、MCP 网关、提示词版本化 ——
要么需要额外运行时，要么是团队产品的能力，跟「单 exe 免安装、给个人和
小团队用」的定位冲突。
